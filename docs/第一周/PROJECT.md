# 企业职工人事在线管理信息系统

## 1. 项目背景
传统企业人事管理多依靠 Excel 表格或者纸质档案，存在信息分散、查询困难、人员权限混乱、员工敏感隐私信息缺少保护、人事变更无日志留痕等问题。为解决上述痛点，开发一套 B/S 架构的企业职工人事在线管理信息系统，实现人事信息线上统一管理，配套权限隔离、敏感字段脱敏、操作审计能力。
系统包含三类角色：系统管理员、人事专员、普通职工；覆盖部门岗位、职工档案、劳动合同、人事调动、薪资、考勤、账号权限等业务模块。
> 本项目为生产实习Vibe‑Coding小组开发项目。

## 2. 技术栈
- 后端框架：SpringBoot + SpringMVC + MyBatis
- JDK 版本：设计基线为 JDK11；实际开发环境采用 JDK 17（Eclipse Temurin）
- 前端框架：Vue3
- 数据库：MySQL 8.0
- 开发工具：Vscode 、Git、Gitee
- AI辅助工具：TRAE（主力）、Cursor / 通义灵码

### Git分支约定
- `master`：主分支，存放稳定可运行版本，禁止直接在此开发，仅通过dev分支合并进来
- `dev`：全体组员开发分支，所有新增、修改工作全部在dev分支完成

## 4. 代码约定
1. Java代码规范：类名使用大驼峰；方法名、变量名使用小驼峰；包名全部小写。
2. 数据库规范：表名、字段名采用小写加下划线命名。
3. 项目分层：controller（控制层）、service（业务层）、mapper（数据访问层）、entity（实体类）、config（配置类）。
4. 安全规范：数据库账号、密钥禁止硬编码，统一写在yml配置文件；身份证、薪资等敏感字段需要脱敏处理；后端必须做权限校验，不能仅依靠前端控制权限。
5. Git提交规范：提交信息格式 `[AI‑辅助] 简述本次修改内容`，描述本次改动功能。

# 第二部分：项目设计决策

> 依据《概要设计说明书》V0.2（2026-09-10 小组评审版）整理，作为开发阶段共同遵守的设计基线；与正文冲突时以本部分评审结论为准。

## 7. 技术选型理由

系统采用前后端分离的分层单体架构（不引入微服务），各选型理由如下：

| 技术选型 | 版本 | 选型理由 |
|----------|------|----------|
| Spring Boot | 2.7.x | 约定优于配置、内嵌 Tomcat、开箱即用，搭建与部署效率高；生态成熟，便于答辩与后期维护（已评审确定 2.7，不使用 3.x） |
| Spring MVC | 随 Boot 集成 | RESTful 接口、参数校验、统一返回与全局异常处理支持完善 |
| Spring Security + JWT | 5.7+ | 天然支持 RBAC 与方法级注解鉴权（@PreAuthorize），契合"三角色隔离 + 本人数据过滤"安全需求；JWT 适配前后端分离，有效期 30 分钟 |
| MyBatis + MyBatis-Plus | 3.5+ | SQL 可控，复杂查询灵活；MP 提供通用 CRUD、分页插件、字段自动填充，减少重复代码 |
| Druid | 1.2+ | 数据库连接池 + SQL 监控，便于开发期排查慢 SQL |
| MySQL | 8.0 | InnoDB 支持事务，utf8mb4 支持完整中文与表情字符；满足 1000 人规模数据存储（已评审由 5.7 升级 8.0） |
| Vue 3 + Element Plus | 3.4+ | 组件丰富、表格/表单/树组件开箱即用，适合后台管理类系统；SPA 前后端分离 |
| Vue Router + Pinia + Axios | - | 动态路由（菜单权限）、状态管理、请求拦截（统一携带令牌、401/403 处理） |
| Nginx | 1.20+ | 托管前端静态资源并反向代理 `/api`，规避跨域；单节点起步即可 |
| JDK | 11 | 与 Spring Boot 2.7 匹配，团队环境统一 |
| Maven | 3.8+ | 依赖与构建管理，jar 包方式部署 |
| 附件存储 | 服务器本地目录 | 本期不引入云 OSS；文件落盘、库存路径与元数据，备份脚本覆盖附件目录 |

**不引入的中间件/方案**：Redis（登录失败计数、字典/权限缓存先用库表与本地缓存实现，控制部署复杂度）；微服务与注册中心；审批流引擎。

## 8. 业务模块划分与依赖关系

经评审，系统共划分为 10 个业务模块（M01~M10）：

| 编号 | 模块 | 主要职责 |
|------|------|----------|
| M01 | 用户账号 | 登录认证、会话、账号生命周期、账号-员工绑定 |
| M02 | 员工档案 | 员工主数据 + 教育/工作/家庭/附件子表 |
| M03 | 部门管理 | 组织层级树维护 |
| M04 | 岗位管理 | 部门下岗位与职级维护 |
| M05 | 劳动合同 | 合同登记、续签、终止、到期预警 |
| M06 | 人事调动 | 调动发起、生效回写员工主数据、轨迹留存 |
| M07 | 薪资管理 | 薪资登记、发放锁定、修改留痕、本人查询 |
| M08 | 考勤管理 | 考勤录入、查询、轻量统计、本人查询 |
| M09 | 请假审批 | 职工申请、人事单级审批、通过联动考勤（需需求变更后保留） |
| M10 | 权限角色 | RBAC、行级/字段级权限、脱敏、审计日志、数据字典 |

**模块依赖边（A 依赖 B）**：

```
M01 → M10        登录加载角色权限；账号分配角色
M01 → M02        账号绑定员工主数据
M02 → M03        员工归属部门
M02 → M04        员工归属岗位
M04 → M03        岗位必须归属部门
M05 → M02        合同主体为员工
M06 → M02        调动生效回写员工部门/岗位
M06 → M03、M04   校验调入部门与目标岗位有效
M07 → M02        薪资归属员工
M08 → M02、M03   考勤归属员工，按部门统计
M09 → M02        请假单归属员工
M09 → M08        审批通过联动写入请假考勤
M09 → M10        审批权限校验
```

M03、M04、M10 为底层被依赖模块，不反向依赖业务模块；M10 以框架横切方式（Security 过滤链、AOP、拦截器）作用于全部模块。

## 9. 模块间调用规则

1. **严格五层、单向依赖**：接入层 → 控制层 → 业务逻辑层 → 数据访问层 → 数据库层；禁止跨层调用（Controller 不得直接调 Mapper）与逆向依赖。
2. **跨模块只走 Service 接口**：模块间调用必须注入对方 Service 接口，禁止跨模块直接操作对方 Mapper 或实体表。
3. **禁止循环依赖**：M02 不得反向依赖 M05~M09；员工离职等占用校验由 M02 调用对方 Service 的查询接口完成。
4. **事务边界在 Service 层**：跨表/跨模块操作（调动生效、请假通过写考勤、合同续签、档案主子表提交）由发起方 Service 以 `@Transactional` 统一包裹，任一失败整体回滚。
5. **对象隔离**：Controller 出入参使用 DTO/VO，禁止数据库实体直接暴露前端；查询统一分页（默认每页 20 条），返回统一返回体（code/message/data）。
6. **横切能力集中实现**：鉴权、脱敏、审计、数据权限由 M10 提供统一组件，业务代码不得自行实现权限判断。
7. **配置外置**：数据库连接、密钥、业务参数统一写在 application.yml（多环境 profile），禁止硬编码。

## 10. 系统全局权限约定

1. **三类角色严格隔离**：
   - 系统管理员：管账号、角色权限、字典、审计日志，**不参与任何人事业务操作**；
   - 人事专员：人事业务数据全权限（部门/岗位/档案/合同/调动/薪资/考勤/请假审批），无账号与角色管理权；
   - 普通职工：只读本人档案、合同、薪资、考勤，可提交/撤销本人请假，仅能修改本人密码。
2. **权限模型**：基于 RBAC（用户-角色-权限），权限点表驱动（菜单/按钮/接口三级），本期每账号分配一个角色，多角色为预留扩展。
3. **双重鉴权**：前端动态路由 + 菜单裁剪仅为体验优化；**一切权限以后端校验为准**，接口级由 Spring Security 注解拦截（未登录 401、越权 403）。
4. **行级数据权限下沉**：普通职工的本人数据过滤在数据访问层统一追加 `employee_id = 当前登录绑定员工`，禁止靠前端传参控制，篡改请求参数访问他人数据一律拦截。
5. **字段级脱敏**：身份证号、银行账号、薪资等敏感字段按角色与上下文差异化脱敏（HR 全量、本人可见【已评审】），注解驱动；身份证号、银行账号落库加密（TypeHandler 写入加密/读取解密）。
6. **认证与会话安全**：密码 BCrypt 不可逆存储；密码 ≥8 位且含字母与数字，不得与最近 3 次历史密码相同；连续错误 5 次锁定 15 分钟；会话闲置 30 分钟失效。
7. **全链路审计**：登录/登出、增删改、密码修改、权限变更、敏感信息查看均记录操作日志（操作人、时间、模块、动作、IP、结果），审计日志业务用户不可修改或删除。
8. **输入安全**：所有外部输入后端 JSR-303 校验；SQL 全部预编译参数；文件上传校验类型与大小；日志与异常中禁止输出明文密码。

## 11. 数据库设计约束规范

1. **命名规范**：库名、表名、字段名一律小写 + 下划线；表名按模块前缀区分（如 `sys_` 系统类、`emp_` 员工类、`hr_` 人事业务类）；主键统一 `id`（BIGINT 自增），外键引用字段命名 `xxx_id`；时间字段 `create_time`/`update_time`。
2. **存储规范**：引擎统一 InnoDB；字符集 utf8mb4、排序规则 utf8mb4_general_ci；所有业务表含公共字段：`id`、`create_time`、`update_time`、`create_by`、`update_by`。
3. **删除策略**：业务表统一逻辑删除（`deleted` 标记，0 正常/1 删除，默认 0），禁止物理删除员工、合同、薪资、考勤等业务数据；员工离职仅状态置位。
4. **完整性约束**：以唯一索引保证业务唯一性——登录账号、职工编号、身份证号、合同编号、职工+薪资月份、职工+考勤日期；层级与关联关系采用**逻辑外键**（已评审：不建物理外键），引用完整性由应用层校验保证。
5. **索引规范**：职工编号、身份证号、合同编号及常用查询列（部门、岗位、月份、日期、状态）建索引；索引数量适度，避免无过滤条件的全表扫描列表查询。
6. **敏感数据**：身份证号、银行账号加密存储；薪资金额使用 DECIMAL(10,2)，禁止浮点类型；附件不入库，仅存文件路径与元数据（原名、大小、上传时间）。
7. **状态与枚举**：状态字段使用 TINYINT/短编码并在注释中写明取值含义；请假类型、出勤状态、合同类型、职级等枚举由数据字典表驱动，不在代码中硬编码。
8. **审计与留痕**：独立操作日志表与薪资修改痕迹表（修改前快照 + 修改后值 + 修改原因 + 操作人 + 时间），只增不改不删。
9. **建表交付**：库表结构以初始化 SQL 脚本为准（放 docs/design/），脚本须可重复初始化；数据库支持定期自动备份与恢复。
