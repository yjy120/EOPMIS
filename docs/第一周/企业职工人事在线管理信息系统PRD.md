## 一、引言

### 1.1 文档目的

本文档为《企业职工人事在线管理信息系统》的产品需求文档（PRD），用于明确系统的业务范围、用户角色以及待解决的关键工程问题，作为后续系统设计、开发实现、测试验收与项目答辩的依据。

### 1.2 项目背景

随着企业规模扩大与人员流动日益频繁，传统基于 Excel 表格与纸质档案的人事管理方式暴露出数据分散、查询困难、统计滞后、数据易丢失与权限难以管控等问题。人力资源部门需要花费大量时间在档案整理、合同到期提醒、薪资核算、考勤统计等重复性事务上，难以聚焦于真正的管理与决策工作。同时，普通职工对本人档案、合同、薪资、考勤等信息的自助查询需求长期得不到满足，信息不透明也容易引发内部矛盾。

因此，企业迫切需要建设一套统一的、集职工档案、劳动合同、人事调动、薪资、考勤于一体的在线人事管理信息系统，实现人事业务的在线化、流程化与数据化，并通过严格的角色权限控制保障人事数据的安全性与私密性。

### 1.3 项目目标

1. 实现企业人事业务（部门、岗位、职工档案、劳动合同、人事调动、薪资、考勤）的统一在线管理，提升人事专员的工作效率。
2. 为系统管理员提供独立的账号与权限管理能力，管理系统用户与角色配置。
3. 为普通职工提供个人档案、合同、薪资、考勤信息的自助查询入口，并支持个人密码修改。
4. 通过严格的权限控制，确保不同角色用户只能访问其职责范围内的数据，普通职工无法越权查看他人人事信息。

## 二、业务描述与用户角色

### 2.1 业务概述

本系统服务于企业内部人事管理全流程，围绕"组织管理 → 人员建档 → 合同签订 → 岗位调动 → 薪资考勤"的主线展开业务。系统将取代传统纸质与 Excel 方式，将所有人事业务数据集中存储在数据库中，由不同角色用户按职责分工完成数据的录入、维护、查询与统计工作。

系统覆盖的核心业务包括：

1. **组织架构管理**：维护企业部门信息与岗位信息，构建层级化的组织结构。
2. **职工档案管理**：建立并维护职工人事档案，记录职工基本信息及变动情况。
3. **劳动合同管理**：登记与管理职工劳动合同，支持到期预警与续签。
4. **人事调动管理**：记录职工在部门或岗位之间的调整过程。
5. **薪资管理**：维护职工的薪资记录，便于查询与核算。
6. **考勤管理**：记录职工日常出勤、请假、加班、缺勤等情况。
7. **系统管理**：管理用户账号、角色与权限，保障系统安全运行。

### 2.2 用户角色

系统共定义三类用户角色，每类角色职责与权限严格分离，互不交叉。

#### 2.2.1 系统管理员

- **角色定位**：系统级管理者，不参与任何具体的人事业务操作。
- **职责范围**：
  - 管理系统用户账号（含创建、停用、重置密码）；
  - 分配与管理用户角色与权限；
  - 维护系统基础数据字典与基础参数；
  - 查看系统操作日志，监控系统运行状态。
- **权限边界**：拥有系统最高权限，但**不负责人事业务**，不能对部门、岗位、职工档案、合同、调动、薪资、考勤等业务数据进行任何操作。

#### 2.2.2 人事专员

- **角色定位**：人事业务的具体操作人员，是系统业务数据的主要生产者与维护者。
- **职责范围**：
  - 维护部门信息与岗位信息；
  - 建立与维护职工档案（基本信息、教育经历、工作经历、家庭关系等）；
  - 登记与管理劳动合同（含签订、变更、续签、终止）；
  - 处理人事调动业务，记录部门或岗位调整过程；
  - 维护职工的薪资记录与考勤记录。
- **权限边界**：对所有人事业务数据具有完整的增删改查权限，但不参与系统账号与权限管理；可查询全量职工的人事数据，但不应修改他人账号信息。

#### 2.2.3 普通职工

- **角色定位**：系统的查询用户，只能查看与本人相关的人事数据。
- **职责范围**：
  - 查看本人的职工档案信息；
  - 查看本人的劳动合同信息；
  - 查看本人的薪资记录；
  - 查看本人的考勤记录；
  - 修改本人的登录密码。
- **权限边界**：**严格禁止查看其他职工的人事数据**；不能进行任何业务数据的增删改操作；除本人密码外，不能修改任何其他信息。

### 2.3 角色权限矩阵（总览）

| 功能模块 | 系统管理员 | 人事专员 | 普通职工 |
|----------|------------|----------|----------|
| 部门管理 | ❌ | ✅ 全权限 | ❌ |
| 岗位管理 | ❌ | ✅ 全权限 | ❌ |
| 职工档案 | ❌ | ✅ 全权限 | ✅ 仅本人（只读） |
| 劳动合同 | ❌ | ✅ 全权限 | ✅ 仅本人（只读） |
| 人事调动 | ❌ | ✅ 全权限 | ❌ |
| 薪资管理 | ❌ | ✅ 全权限 | ✅ 仅本人（只读） |
| 考勤管理 | ❌ | ✅ 全权限 | ✅ 仅本人（只读） |
| 用户账号管理 | ✅ 全权限 | ❌ | ❌ |
| 角色与权限分配 | ✅ 全权限 | ❌ | ❌ |
| 修改个人密码 | ✅ | ✅ | ✅ |

## 三、待解决的复杂工程问题
本系统在总体设计上需要解决的一个核心复杂工程问题为：在超级系统管理员、HR人事专员、普通企业职工三类角色共享同一套职工人事数据并协作完成业务操作的场景下，如何构建一套兼顾"职责分离的细粒度权限控制""敏感个人信息字段级脱敏""跨表人事变更全链路留痕"三位一体的数据安全与合规治理体系。其复杂性在于：第一，三类角色的可见数据范围与可操作权限相互交叉又必须严格隔离（如HR专员可维护职工信息但无权分配账号与角色，普通职工可查询本人信息但无权查看他人薪资），需在RBAC基础上叠加行级与字段级数据权限控制；第二，职工信息分散于职工表、合同表、考勤表、薪酬表等多张关联数据表中，身份证号、银行账号、薪资等敏感字段须按角色差异化脱敏展示，同时保证业务流程中HR专员能够正常使用完整数据，脱敏策略须与业务操作上下文动态匹配；第三，所有人事变更（入职、转正、调岗、调薪、离职）及敏感信息查看行为须形成不可篡改的全链路审计轨迹，既能满足《个人信息保护法》对个人信息处理可追溯、可审计的合规要求，又能作为劳动用工管理的事实举证依据。该问题贯穿数据层、服务层、表现层，需统一设计权限模型、脱敏规则与审计机制并保证三者协同一致，是本系统建设的核心难点。

## 五、非功能性需求

### 5.1 安全性

1. **身份认证**：所有用户必须通过账号密码登录才能访问系统，登录密码需采用不可逆加密算法（如 BCrypt）存储，禁止明文保存。
2. **权限控制**：系统基于 RBAC 模型实现菜单级与接口级的双重权限校验，三类角色严格隔离；普通职工访问数据时，后端必须依据当前登录用户身份对每一次查询、修改、删除请求进行"本人数据"过滤，禁止通过修改请求参数遍历或拼接他人数据。
3. **会话管理**：系统采用 Session 或 Token 机制维持登录态，闲置超过 30 分钟自动退出；密码错误连续 5 次后锁定账号 15 分钟，防止暴力破解。
4. **密码策略**：用户密码长度不低于 8 位，须包含字母与数字；修改密码时禁止与最近 3 次历史密码相同。
5. **越权防护**：所有关键业务接口（档案、合同、调动、薪资、考勤）必须在数据访问层校验当前用户对目标记录的访问权限；菜单级裁剪仅作为前端体验优化，不作为安全手段。
6. **操作审计**：对登录、退出、新增、修改、删除、密码修改、权限变更等关键操作进行日志记录，日志不可被业务用户修改或删除。
7. **数据安全**：关键业务数据（身份证号、薪资）在数据库中需进行加密或脱敏处理；日志与异常信息中不得输出明文密码。
8. **输入安全**：所有外部输入必须进行合法性校验与防注入处理（SQL 注入、XSS、文件上传类型校验等），防止恶意输入绕过业务校验。

### 5.2 性能

1. **响应时间**：在 100 个并发用户、5000 条业务数据的条件下，单一列表查询页面响应时间不超过 2 秒，单一新增/修改/保存操作响应时间不超过 1.5 秒。
2. **并发能力**：系统应支持至少 50 个用户同时在线、20 个用户并发操作业务功能时保持稳定运行，不出现明显卡顿或数据错误。
3. **分页与索引**：所有列表查询必须使用分页机制，单页默认 20 条；职工编号、身份证号、合同编号等关键字段需建立数据库索引以保证检索效率。
4. **资源占用**：系统在正常业务负载下，服务器 CPU 使用率不超过 70%，内存使用率不超过 80%。

### 5.3 易用性

1. **操作方式**：系统以 Web 浏览器为主要操作终端，关键业务功能（新增、保存、查询、导出、删除）应同时支持鼠标点击操作与键盘快捷键（Enter 保存、Esc 关闭弹窗等）。
2. **界面风格**：界面整体风格统一、布局清晰，主色调与字体规范一致；表单采用左对齐标签，错误提示以红色文字就近显示在字段下方。
3. **引导与提示**：关键操作（删除、提交、密码修改）需提供二次确认；保存、提交成功后需给出明确的成功提示。
4. **反馈及时性**：用户提交操作后系统应在 1 秒内给出"提交成功"等基础反馈；列表与表单数据加载过程中需显示加载状态。
5. **帮助文档**：系统应内置帮助中心或操作说明，描述各模块的操作流程，便于用户快速上手。
6. **国际化与本地化**：系统默认使用简体中文，日期、金额等格式遵循中国大陆习惯（yyyy-MM-dd、¥）。

### 5.4 可维护性

1. **架构分层**：系统采用清晰的分层架构（表现层、业务层、数据访问层），各层职责单一、依赖方向明确，便于独立维护与替换。
2. **代码规范**：源代码遵循统一的编码规范，类、方法、变量命名做到见名知意；关键业务方法须包含必要的注释说明。
3. **配置外置**：数据库连接、日志级别、业务参数等应通过外部配置文件管理，不在代码中硬编码，便于不同环境间快速切换。
4. **日志体系**：系统提供分级日志（DEBUG/INFO/WARN/ERROR），关键业务异常需记录到日志文件，便于运维与排障。
5. **扩展能力**：权限模型、业务模块设计需考虑后续扩展（如新增角色、新增业务模块），尽量避免硬编码业务逻辑。
6. **文档交付**：系统需随源代码一并提供部署说明、数据库初始化脚本与用户操作手册。

### 5.5 可靠性

1. **数据完整性**：所有业务操作必须保证事务一致性，关键业务（人事调动生效、薪资发放、考勤批量录入）失败时须回滚到操作前状态，不得出现脏数据。
2. **数据校验**：系统须对关键字段（身份证号、手机号、日期范围、金额正负、唯一编号等）进行前端 + 后端双重校验，防止非法数据进入系统。
3. **容错能力**：系统在数据库连接失败、网络异常等异常情况下，应给出明确提示而非崩溃；表单填写过程中异常不应导致已填写数据丢失。
4. **备份与恢复**：数据库应支持定期自动备份，关键数据可在异常情况下从备份恢复，保障数据不丢失。
5. **登录稳定性**：系统应保证 7×24 小时稳定运行，常规维护操作可在不中断服务或短时中断的情况下完成。

## 六、系统约束与系统边界

### 6.1 系统约束

1. **部署架构**：系统采用 B/S 架构，用户通过浏览器访问，服务器集中部署；客户端无需安装专用软件。
2. **技术栈约束**：本系统基于主流 Java Web 技术体系开发（后端采用 Spring Boot + Spring MVC + MyBatis，前端采用 Vue 或 Thymeleaf，数据库采用 MySQL 8.0），服务器使用 Nginx + Tomcat 部署。
3. **开发环境约束**：开发与运行平台为 Windows / Linux，JDK 版本不低于 JDK 11，开发工具建议使用 Vscode。
4. **浏览器约束**：系统须兼容主流浏览器（Chrome 90+、Edge 90+、Firefox 88+），不强制支持 IE 浏览器。
5. **网络约束**：系统部署于企业内部网络，无需对外公开访问；如需远程访问，应通过 VPN 接入。
6. **数据规模约束**：系统应能稳定支撑 300 名以内职工规模的人事业务数据存储与查询。

### 6.2 系统边界

#### 6.2.1 本版本实现范围（In-Scope）

1. **账号权限管理**：用户账号的创建、查询、修改、停用、密码重置；角色与菜单权限的分配；登录、登出、密码修改。
2. **部门与岗位管理**：部门与岗位信息的新增、查询、修改、删除及组织结构维护。
3. **职工档案管理**：职工基本信息（编号、姓名、性别、出生日期、身份证号、联系方式、部门、岗位、职级、入职日期等）的录入、查询、修改、删除与分页展示。
4. **劳动合同管理**：合同的登记、查询、修改、续签、终止，合同到期提醒，以及合同状态的全生命周期管理。
5. **人事调动管理**：调动的发起、查询、修改、撤销，以及调动生效后职工所属部门与岗位信息的同步更新。
6. **薪资信息登记**：人事专员可登记、查询、修改、删除职工的薪资信息（薪资月份、基本工资、岗位工资、绩效工资、补贴、扣款、实发工资、发放日期等）；普通职工可查询本人的薪资记录，支持按月份区间检索。
7. **考勤记录管理**：人事专员可对考勤记录进行录入、查询、修改、删除，按职工、日期范围、部门等条件组合查询；普通职工可查询本人的考勤记录。
8. **本人数据隔离**：普通职工严格仅能查看本人档案、本人合同、本人薪资、本人考勤记录，并可修改本人密码。
9. **操作日志审计**：关键操作日志的记录与查询。

#### 6.2.2 本版本不实现范围（Out-of-Scope）

1. **薪资自动核算**：本版本不实现基于考勤、绩效、税率等规则的薪资自动计算功能，薪资数据由人事专员手动登记。
2. **复杂考勤规则**：本版本不实现 GPS 定位打卡、人脸识别、外勤签到等高级考勤方式，不实现迟到/早退/加班等异常自动判定规则，考勤状态由人事专员人工录入。
3. **审批流程引擎**：本版本人事调动、合同续签等业务不引入多级审批流，由人事专员直接操作完成。
4. **薪酬报表与统计**：本版本不实现部门薪资汇总、人均成本、薪酬报表等数据分析功能。
5. **移动端 App 与小程序**：本版本仅提供 Web 端访问，不提供原生移动 App 或微信小程序。
6. **与第三方系统对接**：本版本不与钉钉、企业微信、飞书、个税系统、银行代发等外部系统进行对接集成。
7. **多组织 / 多租户**：本版本仅服务于单组织企业内部人事管理，不支持多公司、多租户、集团化多组织模式。
8. **高级人事业务**：本版本不实现招聘管理、培训管理、绩效管理、社保公积金管理等扩展人事业务模块。

#### UC-001 用户登录

- **用例ID**：UC-001
- **参与者**：系统管理员 / 人事专员 / 普通职工
- **前置条件**：1) 用户已拥有系统账号； 2) 用户处于未登录状态； 3) 系统正常运行。
- **主成功场景**：
  1. 用户打开系统登录页；
  2. 用户输入账号与密码；
  3. 用户点击"登录"按钮；
  4. 系统校验账号存在且密码正确；
  5. 系统校验账号状态为"正常"；
  6. 系统创建会话，跳转至对应角色的首页。
- **异常流**：
  - 4a) 账号不存在：提示"账号或密码错误"；
  - 4b) 密码错误：提示"账号或密码错误"，连续错误 5 次后锁定账号 15 分钟；
  - 5a) 账号被停用：提示"账号已停用，请联系系统管理员"；
  - 6a) 系统异常：提示"登录失败，请稍后重试"，并记录错误日志。

#### UC-002 修改个人密码

- **用例ID**：UC-002
- **参与者**：系统管理员 / 人事专员 / 普通职工
- **前置条件**：用户已成功登录系统。
- **主成功场景**：
  1. 用户进入"个人中心 → 修改密码"页面；
  2. 用户输入旧密码与新密码（两次）；
  3. 用户点击"保存"；
  4. 系统校验旧密码正确；
  5. 系统校验新密码符合密码策略（≥8 位、含字母与数字）；
  6. 系统校验新密码与最近 3 次历史密码不同；
  7. 系统更新密码并提示"密码修改成功，请重新登录"；
  8. 系统强制退出登录。
- **异常流**：
  - 4a) 旧密码错误：提示"旧密码错误"；
  - 5a) 新密码不符合策略：提示具体规则要求；
  - 6a) 新密码与历史密码重复：提示"新密码不能与最近 3 次使用过的密码相同"；
  - 7a) 两次新密码不一致：提示"两次输入的新密码不一致"；
  - 8a) 数据库异常：提示"密码修改失败"，保留会话不退出。

- **参与者**：系统管理员

  1. 人事专员进入"薪资管理 → 新增"页面；
  2. 选择目标职工，填写薪资月份、基本工资、岗位工资、绩效工资、补贴、扣款、实发工资、发放日期等；
  3. 系统校验字段非空、金额为非负数、薪资月份与职工组合在同月份不重复；
  4. 保存后薪资记录出现在列表中，可按月份、职工、部门查询。
- **异常流**：
  - 3a) 必填项未填写：提示"请填写完整信息"；
  - 3b) 金额为负数：提示"金额不能为负"；
  - 3c) 同月份已存在薪资记录：提示"该职工在本月已存在薪资记录"；
  - 4a) 系统异常：提示"保存失败"，事务回滚。

#### UC-015 录入考勤记录

- **用例ID**：UC-015
- **参与者**：人事专员
- **前置条件**：人事专员已登录，目标职工存在有效档案。
- **主成功场景**：
  1. 人事专员进入"考勤管理 → 新增"页面；
  2. 选择目标职工与考勤日期，填写出勤状态（出勤/迟到/早退/请假/加班/缺勤）、请假类型、加班时长、备注等；
  3. 系统校验同一职工同一日期不允许重复记录；
  4. 保存后考勤记录出现在列表中，可按职工、日期范围、部门组合查询。
- **异常流**：
  - 3a) 同一日期已存在记录：提示"该职工当日已存在考勤记录"；
  - 3b) 考勤日期为未来日期：提示"考勤日期不能晚于今天"；
  - 4a) 系统异常：提示"保存失败"，事务回滚。

#### UC-016 职工查询本人薪资

- **用例ID**：UC-016
- **参与者**：普通职工
- **前置条件**：普通职工已登录，且与系统中的职工档案存在绑定关系。
- **主成功场景**：
  1. 普通职工进入"我的薪资"页面；
  2. 选择月份区间作为查询条件；
  3. 系统根据当前用户自动过滤出本人的薪资记录并分页展示；
  4. 职工可查看薪资详情。
- **异常流**：
  - 2a) 未选择月份：默认列出最近 12 个月；
  - 3a) 当前用户未绑定职工档案：提示"暂未查询到您的薪资信息"；
  - 4a) 职工尝试通过 URL 访问他人薪资：后端拦截并返回"无权访问"提示。

#### UC-017 职工查询本人考勤

- **用例ID**：UC-017
- **参与者**：普通职工
- **前置条件**：普通职工已登录，且与系统中的职工档案存在绑定关系。
- **主成功场景**：
  1. 普通职工进入"我的考勤"页面；
  2. 选择月份区间作为查询条件；
  3. 系统根据当前用户自动过滤出本人的考勤记录并分页展示；
  4. 职工可按出勤状态筛选。
- **异常流**：
  - 2a) 未选择月份：默认列出最近 1 个月；
  - 3a) 当前用户未绑定职工档案：提示"暂未查询到您的考勤信息"；
  - 4a) 职工尝试通过 URL 访问他人考勤：后端拦截并返回"无权访问"提示。
