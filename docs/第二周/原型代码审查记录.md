## 3. 阻断级问题（P0 · 必须整改，否则禁止进入业务开发）

### P0-1 `DataInitRunner` 在生产环境也会重置用户密码

- **位置**：[DataInitRunner.java:46-53](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/config/DataInitRunner.java#L46-L53)
- **现象**：每次启动都会执行 `ensureUser`，对 `admin / hr01 / emp01` 进行"密码是否匹配默认明文"判断，不匹配则**强制覆盖**。
- **风险**：开发/演示/生产共用同一份 jar 包时，**生产数据库的 admin 密码会被演示默认值覆盖**。当前已通过 `@Value` 注入 `password.initial` 但**未被使用**，形同摆设。
- **整改要求**：
  1. 用 `spring.profiles.active` 区分环境，仅在 `dev` profile 下执行；
  2. 或在 jar 启动参数中加开关 `-Ddata.init.enabled=false`（缺省 false）；
  3. `@Value("${password.initial}")` 要么用上，要么删除；
  4. 单元测试中加一个"生产 profile 跑过去不会触发"的反向断言。

### P0-2 JWT 密钥与数据库口令明文写在仓库 `application.yml`

- **位置**：[application.yml:21,43](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/resources/application.yml#L21)
- **现象**：
  - `datasource.password: "123456"` 直接入库
  - `jwt.secret: eopmis-jwt-secret-2026-please-replace-in-production-env-xxxxxxxxxxxxxxxxxx` 也是写死字符串
- **风险**：
  1. 仓库一旦外泄（实习员工误推 / 公开镜像），数据库主密码即被读出；
  2. JWT 密钥长度仅 75 字符，`Keys.hmacShaKeyFor` 对 HS512 至少需要 64 字节，**当前值勉强够**，但若有人再"清理"注释就会直接报错，且无轮换机制。
- **整改要求**：
  1. `application.yml` 中只保留占位符 `${DB_PASSWORD}` / `${JWT_SECRET}`；
  2. 通过环境变量 / `application-{profile}.yml`（不进 git） / Spring Cloud Config / Vault 注入；
  3. 在 `.gitignore` 中加入 `application-local.yml`、`application-prod.yml`；
  4. 编写 README 一节"密钥管理"，并在 CI 阶段做"明文扫描"拦截。

### P0-3 `SecurityConfig` 启用旧版 API，存在未来升级断裂风险

- **位置**：[SecurityConfig.java:49-69](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/security/SecurityConfig.java#L49-L69)
- **现象**：使用 `csrf().disable() / cors().and() / authorizeRequests() / antMatchers()` 的链式风格（自 Spring Security 5.7 标记为 deprecated，6.0 移除）。
- **风险**：项目一旦升 Spring Boot 3.x / Spring Security 6.x，**编译就直接失败**，届时批量改写。
- **整改要求**：切换为 lambda DSL：
  ```java
  http.csrf(csrf -> csrf.disable())
      .cors(Customizer.withDefaults())
      .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
      .authorizeHttpRequests(a -> a.requestMatchers(
              "/auth/login", "/auth/captcha",
              "/doc.html", "/webjars/**", "/v2/api-docs", "/error").permitAll()
          .anyRequest().authenticated())
      ...
  ```
  并在 PR 描述中记录"预留 Spring Security 6 升级通道"。

## 4. 高风险问题（P1 · 强烈建议在业务编码前完成）

### P1-1 `CorsConfig` 开发期配置直接带入运行

- **位置**：[CorsConfig.java:17-24](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/config/CorsConfig.java#L17-L24)
- **现象**：`addAllowedOriginPattern("*")` + `setAllowCredentials(true)`，注释承认"生产应由 Nginx 统一代理"，但代码未做任何 profile 区分。
- **整改**：仅在 `dev` profile 下加载该 Bean；生产用 Nginx `add_header Access-Control-Allow-Origin` 精确匹配。

### P1-2 `JwtAuthFilter` 解析失败完全静默

- **位置**：[JwtAuthFilter.java:50-52](file:///c:/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/security/JwtAuthFilter.java) (此处改 `c:`)
- **现象**：`catch (Exception ignore) {}`，对过期、签名错误、格式错误无任何日志。
- **风险**：被伪造 / 篡改的 token 在审计日志中**没有任何痕迹**，攻击排查困难。
- **整改**：用 `log.debug` 或 `log.warn`（避免日志爆量）记录原因；将 `username` 写入 MDC 便于审计。

### P1-3 `CurrentUser` 每次调用都查库，存在 N+1 风险

- **位置**：[CurrentUser.java:21-31](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/security/CurrentUser.java#L21-L31)
- **现象**：`require()` 每次都 `userMapper.selectByUsername(username)`。
- **风险**：登录后用户被禁用、改密后，**单次请求内部多次调用**才能感知；且未来 Controller 多处调用就会 N+1。
- **整改**：用 `RequestContextHolder` + `ThreadLocal` 缓存当前用户；或在 JwtAuthFilter 中已查到用户时直接塞到 `auth.getPrincipal()`，再写一个 `getPrincipal()` 工具。

### P1-4 `LoginUser.permissions` 字段未被使用

- **位置**：[LoginUser.java:23,28-31](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/security/LoginUser.java#L23-L31)
- **现象**：字段 `permissions` 已声明，但 `getAuthorities()` 只返回了 `ROLE_xxx`，**没有把权限码塞进 `GrantedAuthority`**。前端依赖的 `sys:user:view` 等权限码在 `JwtAuthFilter` 同样被丢弃。
- **风险**：`@PreAuthorize("hasAuthority('sys:user:view')")` 这种注解**永远为假**，业务层一旦切到注解鉴权会"看起来有权限但实际没有"。
- **整改**：
  1. `JwtUtil` 在生成 token 时把 `permissions` 数组塞进 claims；
  2. `JwtAuthFilter` 解析后用 `permissions.stream().map(SimpleGrantedAuthority::new)` 注入；
  3. `LoginUser.getAuthorities()` 返回完整集合。

### P1-5 `application.yml` 在生产也会输出完整 SQL

- **位置**：[application.yml:33](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/resources/application.yml#L33)
- **现象**：`log-impl: org.apache.ibatis.logging.stdout.StdOutImpl` + `com.eopmis: debug`。
- **风险**：密码字段（虽然已 BCrypt）、身份证、手机号、审计日志的 `detail` 字段会被全文打印。
- **整改**：用 `application-{profile}.yml` 三档（dev / test / prod）分别定义；`prod` 关闭 SQL 日志，至少把日志脱敏。

## 5. 中风险问题（P2 · 建议在第一个业务模块 PR 前完成）

### P2-1 `DataInitRunner` 中 `codeToId` 用 id 模拟 code 查

- **位置**：[DataInitRunner.java:60-72,77-84](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/config/DataInitRunner.java#L60-L72)
- **现象**：注释自承"角色没有按 code 查的方法，简单按 id 1/2/3"。一旦角色表里 id 漂移（有人手动调顺序、批量导入），seed 数据会错位。
- **整改**：在 `SysRoleMapper` 增加 `selectByCode(@Param("code") String code)`，并对应 XML。

### P2-2 `GlobalExceptionHandler` 缺两类常见异常

- **现象**：未处理 `ConstraintViolationException`（`@RequestParam @Validated` 用得到）、`HttpMessageNotReadableException`（JSON 解析错误）、`MissingServletRequestParameterException`。
- **风险**：以上三类异常会落到兜底 `Exception` 分支返回 500，前端拿到"系统异常，请稍后重试"，**调试成本高**。
- **整改**：补 3 个 `@ExceptionHandler`，分别返回 400 + 友好提示。

### P2-3 `BizException` 默认 code 500 与 HTTP 500 冲突

- **位置**：[BizException.java:14-15](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/common/BizException.java#L14-L15)
- **现象**：`new BizException("msg")` 默认 code=500。
- **风险**：业务异常被前端误以为是"系统崩了"。
- **整改**：业务默认 code 改为 1000 系列（如 1xxx=业务错误、2xxx=权限、3xxx=第三方），HTTP 状态由 `GlobalExceptionHandler` 映射（code>=1000 && code<2000 → 400；其他 → 500）。

### P2-4 前端 `useUserStore` 在模块顶层调用，初始化顺序耦合

- **位置**：[router/index.js:2](file:///c:/Users/Lenovo/Desktop/EOPMIS/frontend/src/router/index.js#L2)
- **现象**：`import { useUserStore } from '@/store/user'` 在文件顶层执行，依赖 Pinia 已 `createPinia()`。当前 `main.js` 中 `app.use(createPinia())` 早于 `app.use(router)`，所以能跑通，但**易碎**。
- **整改**：在 `router.beforeEach` 内调用 `useUserStore()`；模块顶层 import 会导致 SSR / 单元测试时直接报错。

### P2-5 前端 `request.js` 401 时 `localStorage.clear()` 太粗暴

- **位置**：[store/user.js:43-53](file:///c:/Users/Lenovo/Desktop/EOPMIS/frontend/src/store/user.js#L43-L53)
- **现象**：`clear()` 调用 `localStorage.clear()`，会把其它子系统（如未来的"主题" `theme`、`locale`）也清掉。
- **整改**：用按 key 清除（`removeItem('token')` 等）或前缀（`eopmis:*`）。

### P2-6 前端 `main.js` 全量注册 Element Plus 图标

- **位置**：[main.js:16-18](file:///c:/Users/Lenovo/Desktop/EOPMIS/frontend/src/main.js#L16-L18)
- **现象**：`Object.entries(ElementPlusIconsVue)` 全量注册 ~270 个图标，首屏 bundle 增大 ~400KB。
- **整改**：按需 import，迁到 `unplugin-icons` 或在 `unplugin-vue-components` 中加 `IconResolver`。

### P2-7 `vite.config.js` 缺 `host: true` 与环境变量切换

- **位置**：[vite.config.js:17-25](file:///c:/Users/Lenovo/Desktop/EOPMIS/frontend/vite.config.js#L17-L25)
- **现象**：未暴露给局域网、没区分 `dev` / `prod` 代理目标。
- **整改**：增加 `host: true`、`server.host` / `preview.host`；通过 `loadEnv(mode, ...)` 注入 `VITE_API_BASE`。

### P2-8 `Result` 与前端 `data.code` 协议未文档化

- **位置**：[common/Result.java:11-39](file:///c:/Users/Lenovo/Desktop/EOPMIS/backend/src/main/java/com/eopmis/common/Result.java#L11-L39)
- **现象**：只有 `code=0` 表示成功；前端硬编码了 `if (data.code === 0)`，但**没有任何文档**说明 code 段位。
- **整改**：写一份 `docs/前后端接口约定.md`，定义 code 段位（1xxx 业务、2xxx 权限、4xxx 资源、5xxx 系统）；前端封装 `isSuccess()` 工具。
