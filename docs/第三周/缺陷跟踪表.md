## DEF-001

- **严重等级**：P0-阻塞
- **模块**：UC-005 部门管理
- **缺陷标题**：sys_dept 名称双重 UTF-8 编码（hex `C3A6 E282AC C2BB...`）
- **发现时间**：2026-09-14 I-3 字符集修复迭代
- **发现方式**：测试用例 TC-005-004（部门树接口）— hex 比对失败
- **影响范围**：
  - 所有 sys_dept.name / sys_dept.leader 字段
  - 部门管理页面表格、el-tree-select、API 返回
  - 间接影响 UC-006 岗位管理的 deptName 冗余字段
### 复现步骤
1. 通过 `mysql.exe` 查询 sys_dept 表的 name 字段 hex：
   ```sql
   SELECT id, name, HEX(name) FROM sys_dept;
   ```
2. 期望 hex：`E680BB E585AC E58FB8`（"总公司"的 UTF-8 字节）
3. 实际 hex：`C3A6 E282AC C2BB C385 C692 C2A4 E2 80 98 C3A4 C2B8 C2AD`（双重编码）
### 复现提示词
> 帮我实现部门管理模块。数据库表 sys_dept（utf8mb4 字符集），用 PowerShell 脚本把部门种子数据（总公司、研发中心、人力资源部、财务部、后端组、前端组）导入 MySQL，字符集要保证中文正常显示。注意 MySQL 服务端字符集配置，导入时不要出现乱码。
### 根本原因
- MySQL 服务端默认字符集 `latin1`（my.ini 第 101 行 `# character-set-server=` 被注释）
- sys_dept 表是 `utf8mb4`，但导入时 PowerShell 把 UTF-8 字节流当 GBK 编码发给 mysql.exe
- 服务端 `latin1 → utf8mb4` 转换被错误触发，导致**双重编码**
### 修复方案
```sql
UPDATE sys_dept
SET name = CONVERT(BINARY CONVERT(name USING latin1) USING utf8mb4),
    leader = CONVERT(BINARY CONVERT(leader USING latin1) USING utf8mb4);
```
用 `BINARY` 强制将已"latin1 化"的字节重新按 latin1 解读，再转回 utf8mb4。
### 验证
- 重新查询 hex：`E680BB E585AC E58FB8` = "总公司" ✅
- 浏览器实测：部门表格显示"总公司、研发中心、人力资源部、财务部、后端组、前端组" ✅
### 闭环状态
✅ **已闭环**（2026-09-14 16:07 完成修复 + 验证）

## DEF-002

- **严重等级**：P0-阻塞
- **模块**：UC-006 岗位管理
- **缺陷标题**：sys_position 新增中文被替换为 `?`（hex `3F3F3F3F3F`）
- **发现时间**：2026-09-14 I-2 系统重启后冒烟测试
- **发现方式**：测试用例 TC-006-004（新增岗位-成功）— 写入后查 DB
- **影响范围**：
  - 所有 sys_position.name / description / level 字段
  - 岗位管理页面表格、新增岗位对话框、API 返回
### 复现步骤
1. POST `/api/hr/position` 请求体：`{"deptId":2,"name":"高级工程师测试","code":"PG002"}`
2. 返回 id=2，看似成功
3. 查询 DB：
   ```sql
   SELECT name, HEX(name) FROM sys_position WHERE id=2;
   ```
4. 期望 hex：`E9AB98 E7BAA7 E5B7A5 E7A88B E5B888 E6B58B E8AF95`
5. 实际 hex：`3F3F3F3F3F3F3F`（全部为 `?`，MySQL 转换失败占位）
### 复现提示词
> 帮我实现岗位管理模块。数据库表 sys_position，支持新增岗位（name、code、description、level、deptId 字段），后端用 JDBC（Druid 连接池）连接 MySQL。新增岗位时把中文名称正确写入数据库，保证存储和返回都不乱码。
### 根本原因
- MySQL 服务端默认 latin1，连接也是 latin1
- JDBC URL `characterEncoding=UTF-8` + Druid `connection-init-sqls` 配置均未生效
- 客户端写入 utf8mb4 字节，服务端尝试 `utf8mb4 → latin1` 转换时无法表示的字符被替换为 `?`
### 修复方案
新增 [DruidCharsetConfig.java](../backend/src/main/java/com/eopmis/config/DruidCharsetConfig.java)：
```java
@PostConstruct
public void forceUtf8mb4() {
    DruidDataSource dds = (DruidDataSource) dataSource;
    dds.setConnectionInitSqls(Arrays.asList("SET NAMES utf8mb4"));
    try (Connection c = dataSource.getConnection();
         Statement s = c.createStatement()) {
        s.execute("SET NAMES utf8mb4");
    }
}
```
主动调用 `setConnectionInitSqls` + 实际跑一次 SET NAMES，覆盖 Druid YAML 配置失效的场景。
### 验证
- 重新 POST 新增岗位（"高级工程师测试"），DB hex = `E9AB98 E7BAA7...` ✅
- API 返回 UTF-8 字节正确 ✅
### 闭环状态
✅ **已闭环**（2026-09-14 16:08 完成修复 + 验证）

- **缺陷标题**：[userStore.js](../frontend/src/store/user.js) 把 `token/userId/permissions/menus` 全部持久化到 localStorage，后端权限变更后用户必须手动 `localStorage.clear()` 才能看到新菜单；本轮新增 12 个菜单/8 个按钮后影响扩大（HR/EMP 双角色均遇到菜单不显示问题，见 DEF-018）
- **发现时间**：2026-09-15 18:40（第三周第二天）→ 持续至 2026-09-18（本轮）
- **本轮触发场景**：用户报"HR 个人中心/修改密码又没了" → 实为 DEF-018（缺绑定），但**根因追溯到 localStorage 缓存**：上一轮已通过 `localStorage.clear()` 临时修复，本轮新菜单/按钮变更再次让用户进退两难

  - 不限于本次 UC-007~017：UC-005/006/009/010~013 阶段改 perm 同样有这个问题（但当时未暴露）

### 复现提示词
> 修改角色权限配置，不清除浏览器缓存，硬刷新页面，查看菜单是否同步更新。
### 根本原因
- [userStore.js](../frontend/src/store/user.js#L6-L14) 注释 `// 持久化到 localStorage，刷新不丢失`，但也导致权限变更不会自动同步
- Vite HMR / Ctrl+Shift+R 硬刷新都**不清 localStorage**
- 后端 LoginResp 接口不带 `permVersion` 字段，前端无法感知权限已变更
### 修复方案（已实施 — 临时）
浏览器 Console 执行 `localStorage.clear()` + 重新登录
