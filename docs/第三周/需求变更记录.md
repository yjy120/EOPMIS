### 关键偏差详情
#### CR-201
- **严重程度**：P0-阻断
- **模块**：全局配置
- **标题**：DataInitRunner 在生产环境也会重置用户密码
- **提出时机**：第二周原型代码审查（[原型代码审查记录 P0-1](../第二周/原型代码审查记录.md#p0-1)）
- **PRD 原文**：
  > #### 5.1 安全性
  > 6. 操作审计：对登录、退出、新增、修改、删除、密码修改、权限变更等关键操作进行日志记录，日志不可被业务用户修改或删除。
- **实现现状**：原型代码 DataInitRunner 在每次启动时执行 `updatePassword("Admin@123")` 等，强制重置
- **是否构成偏差**：**是**
  - PRD §5.1.6 明确"密码修改"需审计 + 不可被业务用户修改/删除
  - 实现层让"启动即重置"违反了 PRD 的密码管理原则
- **影响范围**：所有用户账号（admin/hr01/emp01~emp09）
- **处理结论**：✅ **已闭环**
  - 沿用原型审查 P0-1 修复：DataInitRunner 增加 `forceResetOnStartup` 开关，生产环境置 false
  - 同期完成 A4 修复（密码重置加开关）
- **教训**：PRD"审计性需求"必须显式延伸到**启动/部署**行为约束

---
#### CR-202
- **严重程度**：P0-阻断
- **模块**：全局配置
- **标题**：JWT 密钥与数据库口令明文写在仓库 `application.yml`
- **提出时机**：第二周原型代码审查（原型审查 P0-2）
- **PRD 原文**：
  > #### 5.1 安全性
  > 1. 密码安全：用户密码须使用 BCrypt 加盐哈希存储，禁止明文存储与传输。
- **实现现状**：[application.yml](../backend/src/main/resources/application.yml) 明文 `jwt.secret=...`、`datasource.password=123456`
- **是否构成偏差**：**是**
  - PRD §5.1.1 仅明文说"密码"，未延伸到 JWT 密钥、数据库口令
  - 但"密码安全"原则应普适到所有敏感配置
- **影响范围**：全仓库（含提交历史），存在密钥泄露风险
- **处理结论**：✅ **已闭环**
  - 沿用原型审查 P0-2：密钥走环境变量 `JWT_SECRET` / `DB_PASSWORD`
  - PRD v1.1 补充"密钥管理规范"条目（详见 §6 修订建议）
- **教训**：PRD"安全性"条款必须列举具体覆盖项（密钥、令牌、口令、日志）

#### CR-206
- **严重程度**：P1-高风险
- **模块**：全局配置（CurrentUser 工具类）
- **标题**：CurrentUser 每次调用都查库，存在 N+1 风险
- **提出时机**：第二周原型代码审查（原型审查 P1-3）
- **PRD 原文**：
  > #### 5.2 性能
  > 1. 接口响应：常规查询接口 ≤ 500ms 返回，复杂报表 ≤ 3s 返回。
- **实现现状**：[CurrentUser.java](../backend/src/main/java/com/eopmis/security/CurrentUser.java) 每次 `require().getId()` 都触发 `sys_user` 查询
- **是否构成偏差**：**是**
  - PRD 性能条款未明确"用户上下文获取"是否计入 500ms
  - 但 N+1 是公认性能反模式
- **影响范围**：所有需要 CurrentUser 的接口（UC-001~017 几乎全部）
- **处理结论**：⏳ **持续（架构债务）**
  - 临时方案：依赖 Redis 用户会话缓存（未实现）
  - 长期方案：CurrentUser 改为 ThreadLocal 注入 JWT 解析后的 LoginUser，不查库
- **教训**：PRD §5.2 性能应延伸到"基础设施类操作"的耗时基线

- **严重程度**：P3-建议
- **模块**：数据库
- **标题**：schema-rebuild.sql 早期缺 sys_employee / sys_contract / sys_transfer / sys_salary / sys_attendance 表
- **提出时机**：第三周缺陷修复复审（沿用 E1/C1/D1）
- **PRD 原文**：
  > #### 7.2 用例详述
  > - UC-007 录入职工档案：涉及 sys_employee 表
  > - UC-010 登记劳动合同：涉及 sys_contract 表
  > - UC-013 发起人事调动：涉及 sys_transfer 表
  > - UC-014 登记薪资信息：涉及 sys_salary 表
  > - UC-015 录入考勤记录：涉及 sys_attendance 表
- **实现现状**：schema-rebuild.sql 第一版只到 sys_user/sys_role/sys_menu/sys_role_menu，UC-007+ 实施时陆续补
- **是否构成偏差**：**是**
  - PRD 已列各用例所需表，schema-rebuild.sql 应同步
  - 反映数据库设计文档与 schema 实现存在滞后
- **影响范围**：5 张表的初始化数据
- **处理结论**：✅ **已闭环**
  - 沿用 E1（sys_employee）/ C1（sys_contract + sys_transfer）/ D1（sys_salary + sys_attendance）三次补建

- **模块**：全局（基础设施）

  - 数据迁移逻辑：MariaDB 端有 schema 但无 sys_salary/sys_attendance，MySQL 8.0 端有 schema 但开发用前者连接 → 6 个新接口 `Table 'eopmis.sys_attendance' doesn't exist`

- **处理结论**：✅ **已闭环**
  - [application.yml](../backend/src/main/resources/application.yml) jdbc URL 改为 `[::1]:3306` 强制 IPv6 命中 MySQL 8.0
  - 6 个新接口冒烟测试 100% 通过
- **教训**：
  - JDBC URL 避免 `localhost`/`127.0.0.1` 这类可能命中 IPv4/IPv6 不同实例的写法
  - 本地多 MySQL 实例应**显式分配端口隔离**（3306/3307）而非依赖 IP 协议区分
  - 已写入 [每日迭代日志](每日迭代日志.md) §4.2 待改进项：jdbc URL 走环境变量 + 启动时校验表可见性

## CR-108

- **严重程度**：P1-架构债务
- **偏差类型**：PRD 隐含要求"权限变更后立即生效"，但实现依赖缓存
- **模块**：全局（userStore 持久化机制）
- **标题**：缺 `permVersion` 机制，权限变更后旧登录态缓存无法自动失效
- **提出时机**：用户反馈阶段（"我人事专员、个人中心、修改密码咋又没了呢？"）
- **PRD 原文**：
  > #### 5.1 安全性
  > 5. **越权防护**：所有关键业务接口必须在数据访问层校验当前用户对目标记录的访问权限；菜单级裁剪仅作为前端体验优化，**不作为安全手段**。
- **实现现状**：
  - [userStore.js](../frontend/src/store/user.js) 把 `token/userId/permissions/menus` 全部持久化到 localStorage
  - 后端 LoginResp 不带 `permVersion` 字段
  - 用户权限变更后必须 `localStorage.clear()` + 重新登录
- **是否构成偏差**：**是**
  - PRD 5.1.5 要求"权限校验即时生效"，但前端缓存机制让旧权限持续到用户清缓存
  - 本轮 DEF-018（HR 缺 me:pwd:update 绑定）暴露的就是缓存 vs 新绑定的时间差问题
- **影响范围**：所有角色权限调整场景（UC-001~017）
- **处理结论**：⏳ **持续（架构债务）**
  - 临时方案：浏览器 Console 执行 `localStorage.clear()` + 重新登录
  - 长期方案：LoginResp 加 `permVersion` 字段，userStore init 时比对，版本不一致自动清缓存 + 跳登录
  - 详见 [缺陷跟踪表 DEF-011](缺陷跟踪表.md#def-011)
- **教训**：
  - PRD"权限即时生效"必须配套"前端缓存失效机制"
  - 沿用第三周第二天标注，本轮因权限变更次数增加（HR +7 权限 / EMP +2 权限）影响显著放大
