### 四、问题清单与处置结论

#### P1【退回·严重】删除占用校验"在职职工"为占位空实现

- **位置**：
  - backend/src/main/java/com/eopmis/mapper/SysDeptMapper.java#L48 `@Select("SELECT 0")`
  - backend/src/main/java/com/eopmis/mapper/SysPositionMapper.java#L32 `@Select("SELECT 0")`
- **现象**：countActiveEmployees 永远返回 0，UC-005 异常流 5a 的"在职职工"分支、UC-006 异常流 4a **实际不生效**——即使部门/岗位下有在职职工，删除也会成功
- **违反 PRD**：UC-005 异常流 5a、UC-006 异常流 4a、5.1.5 越权防护
- **处置结论**：**退回**
- **整改要求**：等 `sys_employee` 表（UC-007 范围）建立后，立即改为：
  - 部门：`SELECT COUNT(*) FROM sys_employee WHERE dept_id = #{deptId} AND status = 1 AND deleted = 0`
  - 岗位：`SELECT COUNT(*) FROM sys_employee WHERE position_id = #{positionId} AND status = 1 AND deleted = 0`
- **时限**：必须在 UC-007 完成后补齐，否则 UC-005/006 的删除占用校验形同虚设
- **当前阶段说明**：代码已留 TODO 注释，接受阶段性空实现，但不得作为最终交付

#### P2【修改·中等】关键操作未写审计日志

- **位置**：
  - backend/src/main/java/com/eopmis/service/impl/DeptServiceImpl.java#L84-L144（create/update/delete）
  - backend/src/main/java/com/eopmis/service/impl/PositionServiceImpl.java#L68-L126（create/update/delete）
- **现象**：create/update/delete 均未调用审计日志写入，仅靠 `createBy/updateBy` 字段记录修改人
- **违反 PRD**：5.1.6"对新增、修改、删除等关键操作进行日志记录"
- **处置结论**：**修改**
- **整改要求**：仿照 AuthServiceImpl 的 writeAudit 模式，在 create/update/delete 成功后写一条 sys_audit_log（操作类型=部门新增/修改/删除、岗位新增/修改/删除）。审计写入用 try-catch 隔离，失败不影响主业务

#### P3【修改·中等】validateParent 防环 guard 超限后静默放行

- **位置**：backend/src/main/java/com/eopmis/service/impl/DeptServiceImpl.java#L164
- **现象**：
  ```java
  if (++guard > 1000) break;
  ```
  guard 超过 1000 时直接 break 退出 while 循环，此时不抛异常，等于**放行**了一个可能形成环的 parentId
- **风险**：虽然 create/update 时已先校验 `parentId.equals(selfId)`，正常不会形成环；但 guard 作为防御性编程，超限应判为数据异常
- **处置结论**：**修改**
- **整改要求**：guard 超限时应 `throw new BizException(40053, "上级部门选择非法")` 而非静默 break

#### P4【修改·低】tree() 使用 HashMap 导致 children 顺序不稳定

- **位置**：backend/src/main/java/com/eopmis/service/impl/DeptServiceImpl.java#L55
- **现象**：
  ```java
  Map<Long, DeptTreeNode> map = new HashMap<>();
  ```
  HashMap 无序，同一层级的 children 添加顺序依赖 list 的查询顺序（已按 sort 排序，实际影响小），但 roots 的添加顺序也依赖遍历顺序
- **处置结论**：**修改**
- **整改要求**：改为 `new LinkedHashMap<()` 保证确定性顺序，或在 add children 后按 sort 排序

#### P5【修改·低】toVO 未忽略 createBy/updateBy 字段

- **位置**：
  - backend/src/main/java/com/eopmis/service/impl/DeptServiceImpl.java#L170 `BeanUtil.copyProperties(d, vo, "deleted")`
  - backend/src/main/java/com/eopmis/service/impl/PositionServiceImpl.java#L130
- **现象**：copyProperties 只忽略了 `deleted`，如果 DeptVO/PositionVO 含 createBy/updateBy 字段，这些内部审计字段会暴露给前端
- **处置结论**：**修改**
- **整改要求**：改为 `copyProperties(d, vo, "deleted","createBy","updateBy")`，或在 VO 中不定义这些字段

#### P6【修改·低】需确认 sys_permission 表已插入权限点

- **现象**：前端权限码用 `hr:dept:view/add/edit/delete` 和 `hr:position:view/add/edit/delete`，但需确认 seed_zh.sql 或 sys_permission 表里实际插入了这些权限点，否则 `hasPerm()` 永远返回 false，菜单/按钮不显示
- **处置结论**：**修改**
- **整改要求**：核对 sys_permission 表数据，补齐 `hr:dept:*` 和 `hr:position:*` 共 8 条权限点（4+4），并分配给 HR 角色

- **现象**：schema-rebuild.sql 只建到 sys_dept / sys_position，**没有 sys_employee 建表语句，也没有 hr:employee:view/add/edit/detail/delete 权限点**。一旦用该脚本全新建库：① /hr/employee/page 报表不存在；② HR 登录后菜单无"职工档案"，按钮全部不显示

- **处置结论**：**修改**
- **整改要求**：将 sql/employee.sql 的表结构与 HR 权限点合并进 schema-rebuild.sql，保证单一脚本可全量重建

#### E2【修改·中等】"我的档案"菜单重复插入

- **位置**：sql/employee.sql（菜单 33）与 schema-rebuild.sql（菜单 21）
- **现象**：两条菜单的 perm 均为 `me:profile:view`、path 均为 `/me/profile`；且 33 的 parent_id=0（顶级），旧库执行增量脚本后侧边栏出现两个"我的档案"
- **处置结论**：**修改**

#### E3【修改·中等】档案绑定登录账号零校验

- **位置**：EmployeeServiceImpl#create / #update（原代码直接 copyProperties 落库 userId）
- **现象**：userId 可填任意值：① 可填不存在的账号 ID；② 可把档案绑到 ADMIN/HR 账号（违反三类角色隔离）；③ 同一账号可被多条档案绑定，UC-009 本人档案定位出现歧义
- **违反 PRD**：2.2 角色职责分离、UC-009 前置条件"已为其建立职工档案绑定关系"
- **处置结论**：**修改**
- **整改要求**：userId 非空时依次校验——账号存在、账号角色为 EMPLOYEE、未绑定其他档案（excludeId 排除自身）

#### E4【修改·中等】emp_no / id_card 数据库唯一索引与软删除逻辑冲突

- **位置**：sql/employee.sql 原 `UNIQUE KEY uk_emp_no`、`uk_id_card`
- **现象**：唯一索引不含 deleted 列，档案软删后同编号/同身份证无法重新录入，而 Mapper 的 count 校验带 `deleted=0` 过滤——数据库层与应用层口径不一致，报错信息还会绕过 40071/40072 业务提示
- **处置结论**：**修改**
- **整改要求**：改为普通索引，唯一性由 Service 层 count 校验保证（课设并发量可接受；高并发场景应改用 deleted 纳入唯一键或生成列方案）

#### E5【修改·低】身份证格式、性别/状态取值缺少范围校验

- **位置**：EmployeeCreateRequest.java
- **现象**：身份证号只校验唯一不校验 18 位格式；gender/status 是裸 Integer，可提交 0、5 等非法枚举值
- **违反 PRD**：5.5.2 关键字段双重校验（PRD 明示身份证号为关键字段）
- **处置结论**：**修改**
- **整改要求**：idCard 加 `^\d{17}[\dXx]$` 正则（允许空）；gender 加 @Min(1)/@Max(2)；status 加 @Min(0)/@Max(1)

#### E6【修改·低】账号—档案双向绑定不同步

  - 方案 A：自定义 @Select 写 JOIN sys_employee 的分页 SQL（推荐，性能好）
  - 方案 B：先按 deptId 查 sys_employee 拿到 employeeId 列表，再用 `qw.in("employee_id", empIds)` 过滤

#### D3【修改·中等】UC-016 本人薪资未实现月份区间查询与默认 12 个月

- **位置**：
  - MeController.mySalary L67-L75（无月份参数）
  - SalaryServiceImpl.mySalary L132-L141（返回全部，无过滤）
  - MySalary.vue（无月份选择器）
- **现象**：PRD UC-016 主场景 2 "选择月份区间作为查询条件" + 异常流 2a "未选择月份：默认列出最近 12 个月"，但当前实现：
  - 后端 mySalary 不接收任何月份参数，返回该职工全部薪资记录
  - 前端 MySalary.vue 没有月份选择器，onMounted 直接拉全部
- **违反 PRD**：UC-016 主场景 2 + 异常流 2a
- **处置结论**：**修改（必要修复，留待下一轮迭代）**
- **整改要求**：

  - 未传时默认 `endMonth = 当前月，startMonth = 当前月-12月`
  - Mapper mySalary 的 @Select 增加 `AND s.salary_month BETWEEN #{startMonth} AND #{endMonth}`
  - 前端 MySalary.vue 增加月份区间选择器

#### D4【修改·中等】AttendanceServiceImpl.update 未重放业务校验（未来日期/请假类型/加班时长）

- **位置**：backend/src/main/java/com/eopmis/service/impl/AttendanceServiceImpl.java#L122-L138
- **现象**：update 只校验了"同日期唯一（排除自身）"，但 create 中的以下业务校验在 update 中**全部缺失**：
  - 考勤日期不能晚于今天（3b）
  - status=4 请假必填 leaveType
  - status=5 加班必填 overtimeHours
- **影响**：编辑已存在的考勤记录时，可以把日期改成未来日期、把请假的 leaveType 清空、把加班的 overtimeHours 清空，绕过 create 时的校验
- **处置结论**：**修改（建议性，留待后续迭代）**
- **整改要求**：抽取一个 `validateBusiness(req)` 私有方法，create 和 update 都调用

#### D5【修改·低】AttendanceServiceImpl.myAttendance 存在死代码

- **现象**：方法开头创建了 `QueryWrapper<SysAttendance> qw` 并 `qw.eq("a.employee_id", ...)`，但实际查询用的是 `attendanceMapper.myAttendance(currentUserId)` 自定义 @Select，这个 qw **从未被使用**

#### D6【修改·低】薪资实发工资未由后端校验公式一致性

- **位置**：backend/src/main/java/com/eopmis/service/impl/SalaryServiceImpl.java#create/update
- **现象**：SysSalary 实体注释写"实发工资 = 基本+岗位+绩效+补贴-扣款（由前端计算或 Service 自动计算）"，但 Service 实际**既不计算也不校验**，完全信任前端传入的 actualSalary。如果前端计算错误或被篡改，后端直接落库
- **处置结论**：**修改（建议性，留待后续迭代）**
- **整改要求**：Service 层强制重算 `actualSalary = base + position + performance + allowance - deduction`，覆盖前端传入值；或至少校验 `actualSalary == 计算值`，不一致时抛业务异常

#### D7【修改·低】薪资/考勤 delete 不校验数据归属与状态

- **位置**：
  - SalaryServiceImpl.delete L122-L130
  - AttendanceServiceImpl.delete L140-L148
- **现象**：delete 仅校验记录存在，不区分薪资/考勤的业务状态（如考勤的未来日期、薪资的发放日期等），可直接软删任意记录
- **处置结论**：**修改（建议性，留待后续迭代）**
- **整改要求**：薪资删除可限制 paymentDate 之后不可删（已发放的薪资不可删）；考勤删除可限制 attendanceDate 超过 N 天不可删

| 同月份/同日期唯一性应用层校验 | countByEmployeeMonth / countByEmployeeDate | 带 deleted=0 过滤，与 @TableLogic 配合，避免软删后唯一索引冲突 |
